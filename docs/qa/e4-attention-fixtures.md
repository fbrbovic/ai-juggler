## Findings the corpus forced (recorded, not hidden)

- The first corpus run failed honestly: the Stuck rule fired on
  alive-prompt sessions (silence + low CPU is true of a waiting prompt
  too). Fix: an alive prompt now excludes Stuck — WaitingUser owns it.
  This is why precision/recall gates exist.
- The healthy class originally used synthetic-clock evals over a
  still-flowing process — a dishonest input (the frozen timestamp
  looked 35 s stale). Replaced with a real-exit healthy class plus a
  real-clock live-healthy guard that must never trip across the full
  31 s debounce gap.

## Rules and signatures (as implemented)

- `stuck_no_output`: no output ≥ `stuck_no_output_secs` AND cpu ≤
  `stuck_cpu_max_pct` (unsampled CPU never blocks — silence + stale
  transcript is the primary evidence) AND transcript mtime stale —
  and an alive prompt excludes the rule entirely.
- `waiting_prompt`: prompt-alive output tail (unanswered `(y/n)`,
  `[y/n]`, allow/permission/press-enter patterns; answered markers
  excluded) unchanged ≥ `waiting_prompt_secs`.
- `quota_exit`: non-zero exit + rate-limit signature in the tail
  (`rate limit`, `usage limit reached`, `quota exceeded`, …) — emitted
  immediately, no debounce (an exit is a fact, not a trend).
- Recovery: output resumes → `Running` within one 200 ms activity drain
  (Req.5 budget 300 ms).
- Thresholds: SPEC §5.1 defaults (300 s / 5% / 300 s / 120 s),
  user-tunable via `heuristics.json` in the app data dir; the Settings
  screen UI lands with its own task and writes the same file.
